# 社区贡献接纳与版本回流

本文面向维护者，说明怎样接纳公开贡献并在手动发布时回流源码。贡献者入口见[CONTRIBUTING.md](../../CONTRIBUTING.md)，公开构建入口见[BUILD_SNAPSHOT.md](../../MyApplication/docs/BUILD_SNAPSHOT.md)。

## 仓库与发布边界

私有主工程是日常应用开发的唯一事实源。公开仓应用源码在维护者手动发布版本时更新，`main` 中的应用源码应对应最近一次已公开的版本。PR 检查与评审不会自动触发私有源码导出，也不会触发应用发布。

应用代码 PR 通常先导入私有主工程，保留公开评审记录，直到某个版本实际交付后再关联发行并关闭。公共专属的 README、贡献说明、Issue/PR 模板和 CI 改进可以独立合入；同时涉及应用代码与公共工具时，应说明各自来源，必要时拆开处理。

## 1. 评审公开提议

先核对 PR 基于的公开 commit、关联问题、改动范围、第三方输入和验证记录。公共 CI 的通过只证明实际执行的公共检查，不能当作 HAP 构建、真机运行或完整发布资格。

评审需要确认：

- 公开版本的问题与私有当前实现是否仍相同；如果内部已经修复，应解释对应情况并在发布后补公开版本。
- 补丁是否包含必要源码、测试输入、构建配方和来源；子模块或依赖提交是否可公开取得。
- 新逻辑及其边界是否说明清楚，第三方权利与原作者署名是否保留。
- 贡献者声明的测试与现有证据是否相符，以及私有集成还需补哪些验证。

需要修改时给出具体理由和可验证的目标。尚未决定采用的调查、Draft PR 或原型，继续保持其真实状态，不登记为已集成。

## 2. 导入私有主工程

在独立分支与独占工作树中导入经过认可的修改，不在进行中的构建输入上并行写入。导入前明确公开目录 `MyApplication/` 与私有工程根的路径映射；不能直接把整个公开仓覆盖进主工程。

可以保留原提交或导入补丁，具体方式由改动规模与路径决定。无论采用哪种方式，都需要保留原作者和公开 PR/提交来源：

- 能保留原提交作者时，保留其作者身份；为适配当前工程而新增的提交由实际修改者署名。
- 重新实现或 squash 时，在提交说明中记录 PR URL，并用已有、经核实的作者身份保留共同贡献署名；不要编造作者邮箱。
- 记录原始 public commit 或补丁身份、实际导入的 private commit，以及必要的适配理由。
- 只把实际采用的内容记为已接纳。部分采用、需要重写或暂时延期应逐项说明。

在私有工程完成相应验证并取得真实提交后，将 PR 更新为“已接纳、待发布”。公开回复无需暴露内部工作树路径、设备记录、私有仓访问地址或未发布功能；私有提交映射可以仅保留在内部台账。

维护者可以使用以下回复结构：

> 这项修改已完成评审并导入主工程，当前状态为已接纳、待发布。集成时调整了……；已完成……，尚未验证……。本 PR 保留打开，实际版本发布后会补充公开 commit/tag。当前没有确定的发布日期。

以上是模板，发布回复时必须替换为实际情况。

## 3. 维护可追溯的贡献台账

台账由集成负责人维护，至少记录以下字段。可以复用既有内部记录，无需在公开仓披露私有提交详情。

| 字段 | 用途 |
|---|---|
| PR URL、作者、原始 public commit / patch 身份 | 找回提议、评审和原作者 |
| 基于的公开版本 / commit | 判断导入时的版本差异 |
| 实际 private commit | 证明修改已进入私有工程 |
| 状态与适配说明 | 区分评审、部分采用、已接纳待发布、延期、撤回和已发布 |
| 已执行与未执行的验证 | 保留真实集成边界 |
| 最终公开 commit/tag | 证明该贡献随哪个源码发行交付 |

“已接纳、待发布”需要真实私有提交和集成验证支撑；仅同意方向不够。“已随版本发布”需要实际公开结果，不能提前填写计划中的版本号。后续决定撤回时，保留原记录并解释更正，不删除贡献历史来改变事实。

## 4. 发布前核对采用结果

使用本次实际发布的冻结源码提交形成公开候选，按手动同步流程核对来源和差异。发布工具只管理其声明的源仓路径，公共专属文件应保留；发现与上次导出不同的公开源码修改时，先查明是否已经导入私有工程，再处理冲突。

对台账中“已接纳、待发布”的每项贡献，检查：

1. 本次发布提交确实包含采用后的实现、必要测试与依赖变更。
2. 生成的公开源码保留这些内容，目录筛选或脱敏转换没有漏掉所需输入。
3. 相对原 PR 的实质变化已有解释；未包含、被撤回或延期的部分仍保持对应状态。
4. 本次构建和公开验证实际覆盖了哪些行为，剩余事项在记录中可见。

源码导出清单、公开 Git tag 与发行产物来源应可互相关联。公开 clone 的构建结果与主工程构建、签名、真机运行分别记录；不要把一次同步或 CI 通过描述为完成了未执行的验证。

## 5. 发布后完成回流

确认公开源码、实际版本 tag 及相关发行已可访问，再补入台账中的最终公开 commit/tag，并在原 PR 说明：

- 已包含的版本与公开源码链接；
- 原贡献被采用的范围和有意义的集成调整；
- 尚未交付的部分或后续事项（如有）。

如果公开仓没有执行该 PR 的 GitHub merge，按“已随版本交付”关闭并关联实际结果，不声称该 PR 已 merge。保留原作者、讨论和提交，必要时在发行日志中致谢。不要为了显示合并状态，把已由完整版本同步带回的源码再次合入，制造重复或倒退。

只有独立的公共文档/工具改进，才按它自己的评审结果直接合入；它们不会改变应用源码的手动发版同步节奏。
